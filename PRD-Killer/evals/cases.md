# PRD-Killer 代表性回归用例

仅在维护或升级 Skill 时按改动选择用例，日常处理 PRD 不自动加载或运行。只读评估，生成材料放在独立临时目录，不修改生产代码、不发消息、不发布。独立评估者先读取 Skill、相关输入和必要参考；不给预期答案，维护者再按以下条件核对实际输出。

这些用例提供输入与行为判据，不要求逐字匹配标题，不将静态校验当成行为通过，也不宣称少量案例代表所有业务。

## A：模糊需求、多来源与未估范围

输入：新用户领券，一人一次，库存有限，领完提醒，后台查记录并导出。导出字段/范围未定；截图无法打开，只有文件名“原型-有备注.png”。已有登录，其他代码及新旧情况未知。先交研发分析，不停在提问。

检查：背景与场景置前；资格、限次、库存、提醒、查询、导出各有去向，提醒/导出不能仅留在问题清单；不可读图片明确保留缺口；重要问题说明影响，未估范围不隐入完整总量；不默认采用 Redis/MQ。来源和遗漏在内部核对，正文不要求展示状态矩阵。

## B：痛点与方案错位

输入：客服查不到用户操作结果，产品提出建设消息中心并发短信。用户希望优先减少反复人工查证；现有查询能力和通知需求细节未知。

检查：提出结果查询/查证与消息通知各自改善什么、不能改善什么，比较更小方案；消息中心与短信作为明示提案保留及标记待决策范围，不擅自删除；不虚构人工成本或转化提升。

## C：确认后存量交接

输入：只读 [工单夹具](fixtures/ticket-query/context.md)、[实际片段](fixtures/ticket-query/ticket_query.py) 和 [结构](fixtures/ticket-query/schema.sql)，给新增状态筛选的研发交接稿。

检查：引用真实 list_tickets / handle_list_tickets，区分接口文档来源和代码静态事实；保持 Python/SQLite、权限与响应信封；status 省略、非法值、历史 null、分页前过滤与切换游标语义完整；业务规则与技术实现分章说明，相关依赖清楚；执行计划未冒称通过；工期不凭空承诺。去重后场景仍可独立理解，接口和验收细节不能丢失。

## D：多角色审批

输入：员工提交采购申请，部门经理审批；超过额度还需财务审批；提交后能撤回，审批完成后不能撤回。金额边界、驳回重提和审批人缺席时规则未定。

检查：讲清角色交接、状态变化、撤回与审批竞争；识别金额边界和驳回问题，不自行定数值；不把 SQL 事务或工作流产品当成业务规则；不要把所有流程都套成领券库存问题。

## E：跨系统结果与失败

输入：用户付款后外部平台发放权益，回调可能重复或延迟；用户希望查看处理状态。外部协议还没提供。

检查：区分付款、发放、通知各自状态与数据归属；说明跨系统不能靠一个本地事务保证全部成功；保留外部契约缺口、重复与结果查证，不伪造外部错误码或重试次数。

## F：规则变化后的局部更新

输入：领券从“同活动按账号一次”改为“每月一次且库存按门店独立”，只更新受影响部分；后续产品确认自然月、Asia/Shanghai、跨店共享账号限次。

检查：保留 ID，记录新依据，关闭已明确的周期/时区/跨店问题并替代旧假设；检查唯一约束、库存定位、接口、历史数据、任务、验收、估算与开工状态。历史记录是否计入新限次未定时，识别资格判断与启用条件也可能受阻，不能只归入迁移。不重做未受影响正文，不继续把已确认问题列为待确认。

## G：激活边界

输入：只翻译英文；只修复已定位的小空指针；只解释已有接口字段。

检查：不强制拉起完整图集；明确调用本 Skill 但任务很小时直接处理小任务。分析不自动创建外部文档、安装组件或实施代码。

维护记录应写清所用 Skill 版本/路径、输入、实际输出、观察与修正、复核范围。只有格式校验的结果，不能写成上述用例已通过。

## H：阅读体验、图文与模糊指标

合成输入：运营经常问研发日报是否更新，希望自行查看和刷新。只有截图文字转录“业务日期、处理单量、更新时间、刷新”，要求“最新、秒级可用、100%准确、失败提示”；没有原图、接口或代码，旧值策略、口径、容量与团队未知。

检查：流程、数据、时序和候选架构讲清触发、处理、变化、结果与恢复，渲染可查看图片，短注补原因；转录不能证明接口存在。保留目标，拆分响应/数据延迟、统计来源和时间截面，不编数值；失败不伪装为零。关键接口单独成文，验收可放分析附录，不因固定章节堆长文或无依据排期。

评估产品是否能复述背景、开发能否理解关键规则、测试能否执行验收，并人工检查重复铺陈。该输入只是合成代表案例；用户的实际 PRD 和生成全文未提供时，不能宣称真实案例阅读体验已验证。

## I：图解交接与资金事实

输入：manual付款计划10万元；常规上限为计划余额与已批准收票申请可用额度的较小值；JSD提交占额，批准逐计划生成未开始应付单，重复回调不能重复出单；真实票逐单足额分配后挂账；FKSQ批准后办理实际FK；真实出款才核销；驳回只释放本申请占额；详情保留提交快照，审批重查当前值；台账与履约读同一实际记录。没有代码，要求图为主的Markdown。

检查实际产物：四类视角均有渲染图和编辑源，不依赖阅读器解析Mermaid。业务图不能把JSD批准画成挂账；数据图区分申请额度、实际票、分配、资金事实、快照与当前值；时序标当前复核、自身占用、防重、提交与失败，不凭空补银行转账接口；架构不捏造现有技术栈。正常宽度字号、连线和图高可用，长链拆图。短注补原因，不再逐图抄成故事。

## J：变化范围与规则冲突

输入：上一版本是三万字分析和原型截图。用户要求以图为主，明确收款与付款不同路径；原文一处说新补票自动挂账，另一处说事后补票人工。没有代码，请整理完整需求。

检查：不能只给四张泛图或继续嵌旧截图；收付款分别展开，能从总览定位。冲突分支标待确认，建议与事实区分，不悄悄选一种。主文不以几十项问题和来源日志开场，确定部分继续可读；压缩不丢提醒、导出、取消和恢复等明确诉求。

## K：渲染失败和小需求

输入一：输出Markdown，阅读器不支持Mermaid；已有本地工具可生成SVG和PNG，不允许联网安装。输入二：仅对现有查询增加一个可选状态筛选，身份、参数、分页语义已明确。

检查：前者实际生成并嵌图，不能用语法围栏交差；缺工具先尝试已有替代，如实说明，不自动安装。后者按需给小流程／时序和精确改动，不强行四图或九章。源、图与正文同版；图片存在不等于业务和视觉通过。

## L：分析稿与关键接口契约独立交付

输入：收款登记金额>0；明确计划后联动核销，未挂账YS核销0；允许分次认领且不得超过收款及应收余额；审批回调可能重复。请以图为主输出面向前后端的Markdown交接，交代关键调用、数据与失败。没有工程代码和接口协议，直接继续、不停在提问。

检查实际交付：分析稿与关键接口契约是两个独立文件，双向相对链接有效；分析稿保留业务／时序语义，不出现接口字段字典或错误码清单。契约覆盖登记、认领、结果读取及回调的调用职责、输入输出与相关拒绝／防重要求，业务规则引用分析，不重复整套流程。未知协议写需求级草案，不虚构URL、字段类型、错误码或现有能力；审批作用未知保留缺口。变体：提供C的工程材料时保持实际GET及响应信封；用户明确只要分析或纯文案无接口影响时，不强行生成契约。

## M：默认独立开发清单与进度保留

输入：沿L的完整研发交接请求，但不额外要求任务清单或排期。后续补充已有进度：T01权限范围已核对完成并保留备注，T02登记入口待开发；新增认领并发校验，继续梳理。另给变体：仅翻译一段说明；或明确只要图解分析。

检查：完整研发梳理默认单独交开发顺序清单，分析、契约、清单相互链接；使用可编辑的Markdown复选框，有稳定ID、依赖、完成条件及依据，无循环、不机械套用固定任务数量。无进度证据的任务未勾选；更新保留原ID、完成状态及备注，新任务未勾选，受变更影响的完成项说明复核原因。新增前置可调整展示顺序，不改原ID追求编号递增。不将清单塞入任一附录、不以未要排期为由省略、不复制整套需求和接口。未知规则只阻塞受影响任务；翻译或明确限制输出的变体遵从用户范围，不强制三文档。
