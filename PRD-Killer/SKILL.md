# PRD-Killer

把需求整理成开发者能快速看懂的**图解交接稿**：先看图知道要改什么、数据怎样流转，再用少量文字解释为什么及关键限制。默认以图为主，不能把长篇分析换个标题后再附几张截图。

## 交付优先级

1. **业务正确**：对象、金额、状态、责任与原材料一致；事实、建议、待确认在相关图中直接区分。
2. **图中讲清**：完整且涉及多步骤／多对象的需求，至少覆盖业务流程、数据流转、时序、技术架构四类视角，按独立业务链拆图。
3. **一眼能读**：每张图只回答一个问题，主干、异常、职责和数据标签清楚，正常文档宽度下不靠放大才能阅读。
4. **文字够用**：图下只说明目的、改动及关键边界，不逐节点复述流程。业务字段长表、全量问题和验收放附录；关键接口契约、开发顺序清单分别单独成文。

小范围或局部请求按需选图，不硬凑四张。完整复杂需求也不能以“四张已有”代替覆盖：例如收款和付款有不同状态、资金归属和例外，应分别展开；用户明确点名的图种必须回应。

## 先理解，再构图

读取正文、表格、图片及补充结论，梳理角色、起止、触发、业务对象、关系键、金额／数量、状态及异常。长文可先做内部覆盖清单，不把采集日志、几十项问题或材料清单放在正文开头。

有工程时先查 AGENTS.md、相似实现、接口和数据归属；没有工程时，架构图标注“候选逻辑架构，待工程核实”，数据图标注业务实体，不编造数据库表名、HTTP 路径或已有组件。截图只能证明可见内容，不能证明后台可复用。

对冲突先保留共同确定部分，在影响结果的分支旁标“待确认”，写出差异与影响；给建议时用候选边框／标签。不得为了连通流程替业务方决定规则，也不得把红冲、退款等范围外动作画成一期可用。

补全图的结构不等于补造业务：未说明的审批占用、外部系统、中间状态或逆向动作，不能因为常见就接入确定主链。必要设计标为候选，并注明它依赖的决定。

## 默认工作方式

1. **确定图集**：按 [图解正文模板](references/output-template.md) 安排阅读顺序；为每张图写一句要回答的问题，删除相同信息换皮的图。
2. **建模内容**：按 [图示内容与排版规范](references/visual-design.md) 填全角色、条件、数据、状态及关键失败分支。业务判断看 [业务分析](references/business-analysis.md)，实现边界看 [工程设计](references/engineering-design.md)。
3. **生成图片**：按 [渲染与交付](references/rendering.md) 生成真实 SVG／PNG，并保留 Mermaid、DOT 或原生 SVG 源。已有原型截图只作证据，不能充当新流程图或架构图；技术图不使用图像生成模型绘制文字和箭头。
4. **图旁写短注**：每图通常 2—4 条，回答做什么、为何这样、什么情况下不能继续。需要精确多条件判断时用小表；不再重复一遍整条业务故事。
5. **独立接口交接**：面向研发且涉及关键调用、新增或变更接口时，按 [接口契约](references/api-contract.md) 另交《关键接口契约》；分析稿保留业务动作与时序，契约单独说明输入输出、权限及失败处理。没有工程依据时交需求级草案，不编造路径、字段类型或错误码。
6. **独立开发清单**：面向研发的PRD梳理默认按 [交付与验收](references/delivery-and-validation.md) 另交《开发顺序清单》，不必等用户再要清单或排期。按依赖排序，使用Markdown复选框，写清任务编号、动作、前置、完成条件及关联依据；无工程进度证据时不标已完成，已有清单保留编号、勾选与备注。
7. **检查再交付**：实际打开每张图检查中文、字号、连线、分支和截断；跨图核对同一对象与状态。正文图片、配套文档链接须能打开，各文档的范围、版本和规则一致；检查清单依赖及完成标记，不能只交代码围栏或引用不存在的图片。

写作参照：[完整链路图解](references/example-visual-handoff.md)、[小查询改动](references/example-confirmed-handoff.md) 及其 [独立契约](references/example-confirmed-contract.md)、[开发清单](references/example-confirmed-checklist.md)。示例只展示分析和画法，不能将其中业务规则套到其他需求。清单及验收按 [交付与验收](references/delivery-and-validation.md) 组织。

## 图文组织

正文采用“目标与范围简述 → 业务流程 → 数据流转 → 关键时序 → 技术架构 → 改动与关键决策”的顺序，不是固定九章长文。每节以图承担主要信息，表格只承载确实适合比较的内容。

一般完整需求正文说明文字可先按约 1500—3000 个汉字控制，单图说明通常不超过约 120 字；这是压缩提醒，不是硬性字数门禁。跨业务链应拆图与章节，不能为达字数删掉金额、权限、失败恢复、提醒或导出等明示诉求。

开发者应能从主文找出新增／复用／调整点及原因。少量影响结果的决策放主文；完整来源、业务规则字典、验收和其余待确认项按需附后。接口字段、响应、错误及联调示例维护在独立契约文档；开发顺序与可勾选任务维护在独立清单，不放进分析稿或接口稿附录。工作量和排期按需、有依据再估，不影响默认交付开发清单。

## 交付形态

用户指定格式和目录优先。请求 Markdown 时交付主 `.md`，用相对路径嵌入 `diagrams/*.png`（或目标阅读器支持的 SVG），配套保留矢量图与可编辑源。不要让正文依赖阅读器支持 Mermaid；未要求时不额外交付 HTML、PPT 或 Word。

面向研发梳理PRD时，默认并列交付 `需求图解.md`、`开发顺序清单.md`；涉及关键调用或接口变更再交独立 `关键接口契约.md`。名称跟随业务和版本，相关文档相互链接。分析稿以图讲清做什么、为什么及边界；契约按调用讲清如何对接；清单按依赖讲清先做什么、怎样算完成。时序图可保留必要输入输出语义，不复制契约字段表。业务规则与问题在分析稿统一编号维护，契约与任务引用对应依据，并说明未决事项阻塞哪部分。纯概念解释、翻译或没有研发交接内容的小任务不硬凑清单；用户明确只要某一文档或限制输出范围时遵从。

默认统一浅底矢量风格：业务／界面蓝、处理绿、数据橙、关键风险红、外部系统灰；图例写清虚实线含义。配色、字体、方向和对象命名前后一致，异常不能仅靠颜色区分。

工具确实无法渲染时，先使用已有替代工具；仍失败则明确交付的是“未渲染源稿”和缺失项，不宣称图片完成，不静默退回长文。不得自动安装、联网加载渲染库或上传业务数据；尊重已有授权。

## 交付前判断

- 不读长文，开发能否从图看懂主线、责任、数据读写和关键异常？
- 四类图是否各自提供新信息，而非把同一串方框换四个标题？
- 关键分支是否有条件、有结果、有后续动作？占用、提交、释放、核销等是否清楚？
- 同一关系／状态／金额是否在所有图中一致，待确认和范围外是否清楚标记？
- 关键调用是否独立交接；分析稿是否混入接口字段表或错误码清单；配套文档链接、规则引用及未决问题是否一致？
- 是否另交可勾选开发清单，前置任务存在且无循环，完成条件可核对，已有勾选和备注得到保留，未把文档完成冒称开发完成？
- 正常宽度是否看得清；源文件、渲染图与正文是否同一版本？截图是否与新绘图分开？

复杂关联审查读 [内部核对](references/analysis-controls.md)。维护本 Skill 才读取 [回归用例](evals/cases.md)；不要把内部质量评分或完整检查过程塞进用户正文。分析不自动改业务代码、发布或发消息。
