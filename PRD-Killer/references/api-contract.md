# 关键接口契约：独立交付，保持业务含义

面向研发交接且存在关键前后端、模块、外部或事件调用，或新增／变更接口时使用。交付单独的 `关键接口契约.md`，与 `需求图解.md` 同目录、同范围、同版本并双向链接。用户指定命名与格式优先；没有接口影响或明确只要分析时，不为凑文件生成空契约。

## 两份文档各自承载什么

分析稿用图讲清业务、数据、时序、职责和改动；时序箭头保留动作及必要输入输出语义。关键接口清单、字段定义、响应、错误、权限与联调示例放独立契约，不在分析稿正文或附录重复展开。

业务规则与问题在分析稿统一维护编号。契约引用对应图／章节／问题，并写清影响哪个调用；不能复制整套流程形成第二份需求。规则变更时同步受影响契约，保留已有调用编号及兼容说明。

## 先确定证据级别

- **只有PRD或原型：**标“需求级契约草案，待工程对齐”。用业务动作标识调用方、提供职责、关键业务信息、预期结果与拒绝条件。字段名称有来源才保留；候选命名要说明，未知类型、路径、方法、响应格式和错误码待核实。不生成看似可联调的虚构JSON。
- **已有代码或可靠协议：**引用实际文件／方法／规范，区分复用、修改、新增及候选；核实路径、参数、身份来源、响应信封、错误码、分页与兼容。片段或文档证据不能冒称运行验证。
- **完整接口文档：**仅在需要且技术信息足够时，在同一独立契约文件中深化完整签名、字段和示例；需要OpenAPI等机器契约时另行生成并保持一致，不因PRD分析自动扩成全量API设计。

## 建议的独立文档结构

1. **范围、级别与分析链接：**说明依据、已核实部分、仍待工程确认部分。
2. **关键调用清单：**以业务动作编号，说明调用方→提供职责、用途、触发及关联图；编号不代表必须拆成同等数量的HTTP接口。
3. **必要共用约定：**身份与数据范围、单位／时间、既有协议规范及写入失败处理；按需求保留，避免通用规范堆砌。
4. **逐调用契约：**输入、返回、状态变化、拒绝条件、调用方后续动作；只展开实际涉及的细节。
5. **待确认及验证边界：**引用原问题编号，明确哪些输入、结果或兼容行为因此不能冻结；区分验收设计与实际验证。

## 逐调用需要说清的内容

- 谁调用谁、何时调用、是否可复用已有能力；身份从哪里取得，权限与数据范围如何校验。客户端用户／租户标识不能自行决定权限。
- 输入信息与业务含义；有依据时补字段位置、类型、必填、默认、允许值、单位，以及相关的省略／null／空串语义。
- 返回信息、业务状态、空结果和失败。未知、未处理、结果未明与真实0值不能混用；有协议依据时补成功／失败示例。
- 拒绝条件、调用方处理方式、是否可重试。业务拒绝与系统故障分开；超时先查证是否已提交，不能直接再造业务单。
- 写入或异步调用的重复、并发、结果查询与失败恢复；区分本库提交、跨系统回执及补偿。只读查询不机械增加幂等键。
- 查询的筛选、稳定排序与分页边界；变更涉及的旧参数、旧调用方、历史数据及兼容。

RPC按方法、参数、返回和失败说明；事件补生产／消费方、时机、关联键、重复／顺序和失败；批任务补输入范围、触发、进度和重跑。没有需求依据的异步任务、外部接口或新基础设施不自动加入。

交付前核对双向链接、范围／版本、对象与状态、问题引用。只有实际执行过才能报告接口校验或联调通过。
