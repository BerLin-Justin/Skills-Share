# 交付与验收：任务有边界，结果能核对

## 开发顺序清单 独立交付

面向研发的PRD梳理默认另交 `开发顺序清单.md`，与分析稿及已生成的接口契约同目录、同范围、同版本并相互链接；用户不必再额外要求。清单不塞进分析或接口文档的附录。仅翻译、概念解释、无研发交接内容的小任务或用户明确限制文档范围时按实际要求处理。

按业务依赖分阶段，先共用能力再消费方、先主链再逆向，列明可并行任务和特定分支的阻塞。未决问题只阻塞受影响的任务，确定部分继续；没有代码时标建议顺序及待核实复用点，不编造文件、组件或工期。小需求按实际规模给短清单，不照搬固定任务数。

采用GitHub风格任务列表 `- [ ]`，完成改 `- [x]`。每项有稳定编号、具体动作、前置任务／条件、可观察的完成条件及关联图／契约／规则编号；相关时标负责角色，不虚构具体人员。可追加负责人、日期与实现／验证记录，不强制每项维护空字段。

```markdown
- [ ] **T01 对齐现有能力**。依赖：无。完成：定位真实实现，记录复用点及差异。关联：分析中的开发改动。
- [ ] **T02 实现关键变更**。依赖：T01及对应规则确认。完成：指定输入产生约定结果，关键拒绝分支正确。关联：对应契约／业务图。
- [ ] **T03 联调与交付核对**。依赖：T02。完成：关键场景验证有记录，文档与实现同版。
```

无实际工程进度证据时全部未勾选；分析、接口或清单写完不等于代码实现或验收完成。后续梳理已有需求时保留任务编号、已勾选状态和备注，新增任务未勾选；新增项成为旧任务前置时调整展示顺序，保留原ID，不为编号递增而打乱依赖或重编号。需求变化导致完成条件失效时，仅将受影响项标待复核并说明原因，其他完成项不重置。仅根据用户明确进度或实际核对结果更新完成状态。

检查前置ID存在、无自身／循环依赖，完成条件与引用可核对，链接有效。清单只写执行动作和交付结果，业务规则在分析维护，调用细节在契约维护，避免复制成第三份PRD。参考 [银行收付款开发顺序清单](开发顺序清单.md)。

## 任务与时间

清单说明顺序与依赖，不代表排期。用户需要排期或有可靠工程依据时才展开工作量；不为凑章节生成大量未知工时。按可检查的交付物拆任务，小需求不用按每个文件或方法拆一排任务，大能力包含独立交付物时再拆。

工作量是投入的人日/人时，工期是日历跨度。参考实际代码、同类实绩和团队可用性估算；依赖、共享人员、联调、修复、外部等待都会影响日期，不能直接用总人日除人数。

缺少范围、人员或工程证据时先给任务顺序、条件估算和重估项，不承诺“下周上线”。导出、提醒等未定范围保留任务占位；部分小计说明包含和未包含项，完整总量未知时如实写明。

重要问题用短句说明影响：例如“导出量和字段未定，影响同步/异步方式与工时”；不默认附完整开工状态矩阵。历史数据规则影响当前判断或切换时，应沿依赖说明，而非只归为迁移脚本。

任务完成条件引用业务要求，避免抄写整段实现。遵循用户和项目已有验证规则，单测聚焦高风险边界，不因分析或文档改动自动编译全工程。

## 验收可直接执行

每条关键验收包含前置条件、操作、可观察结果。保留执行必需的输入和预期值；不能只写“符合规则”“功能正常”或一个编号。

从核心场景检查正常、拒绝、重复、竞争、超时、历史数据和权限等相关边界；根据风险选择，不机械填满全部类别。已经在规则中说明的条件无需整段重抄，但验收步骤应独立可操作。

例如业务已确认允许失败后保留旧数据时，可以验收：给定上次成功结果和更新时间，触发刷新且模拟来源超时；页面提示更新失败，保留原数据及原更新时间，并提供约定的后续操作。该前提未确认时先记录候选与影响，不能当成最终验收结论。

## 模糊指标要有测量口径

“秒级可用”先分清查询响应、任务受理、计算完成还是数据新鲜度。明确起止事件、范围/负载、测量方式、目标及未达标处理；缺少目标或容量依据时不编数字。

“100%准确”明确权威来源、统计对象、重复/补录/撤销口径、时间截面及核对方法。口径未定不能承诺，缺失与失败也不能默认为零或有效最新值。

字段单位、日期时区和空值语义在业务规则处统一维护，验收用相应样本核对。未达标时说明业务可接受的提示、重试、保留旧值或人工处理，候选选择需明确。

## 验证与业务效果

区分验证计划与实际执行结果，静态读代码、已明确需求都不等于接口/运行/性能已通过。发布按风险说明顺序、观察和回退，数据改变后不能无依据承诺无损回退。

业务收益有需要时给指标、基线、目标来源和采集办法；功能上线不直接证明咨询减少或效率提升。没有数据时如实待采集，不强制每个需求建设埋点体系。
